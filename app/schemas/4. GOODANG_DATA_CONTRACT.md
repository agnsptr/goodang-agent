# GOODANG DATA CONTRACT

**Project:** Goodang  
**Component:** Data Contract untuk ADK Agent + Temporal  
**Channel:** Telegram  
**Primary Process:** CS Goodang — Guru Ingin Pesan  
**Primary Transaction Log:** `POS_TRANSACTION_LOG`  
**Document Type:** Data / Integration Contract  
**Version:** 1.0  
**Status:** Development Baseline

> **Canonical Contract:** Nama state, tool, error code, schema field, formula, dan idempotency key didefinisikan kanonik di `docs/0. GOODANG_CONTRACT.md` (Single Source of Truth). Dokumen ini adalah SoT untuk **data schema detail**. Jika ada konflik nama, `docs/0` menang.

---

# 1. Purpose

Dokumen ini mendefinisikan kontrak data yang digunakan antara:

```text
Telegram
   ↓
ADK Agent
   ↓
Application / Tool Layer
   ↓
Temporal
   ↓
Goodang Services
   ↓
Database / Transaction Log
```

Tujuan dokumen:

1. memastikan format data antar-komponen konsisten;
2. membedakan data customer, master data, draft order, dan transaction;
3. menetapkan source of truth;
4. mencegah AI mengarang data;
5. menjadi dasar implementasi API, tool, Temporal Workflow, validation, dan database adapter;
6. menjadi dasar mapping ke `POS_TRANSACTION_LOG`.

---

# 2. Important Scope Rule

Kontrak ini hanya menetapkan data yang **sudah diketahui atau diperlukan oleh workflow**.

Jika struktur database/API Goodang belum tersedia atau belum disepakati, field tersebut harus ditandai:

```text
TBD
```

atau:

```text
REQUIRES_SOURCE_OF_TRUTH
```

Jangan membuat schema production berdasarkan asumsi.

# 5. Identity Data

## 5.1 Telegram Identity

Telegram identity digunakan untuk routing conversation, bukan sebagai business customer ID.

Minimum:

```json
{
  "telegram_user_id": "123456789",
  "telegram_chat_id": "123456789",
  "username": "example",
  "first_name": "Imam"
}
```

### Rules

- `telegram_chat_id` digunakan untuk menentukan conversation context.
- `telegram_user_id` digunakan untuk identitas Telegram.
- Jangan menggunakan Telegram ID sebagai `member_id` Goodang.
- Mapping Telegram → Goodang customer harus melalui identity resolution.

# 7. Customer Resolution Result

Tool `identify_customer` harus mengembalikan structured result.

## Success

```json
{
  "ok": true,
  "code": "CUSTOMER_FOUND",
  "data": {
    "member_id": "MBR-050",
    "member_name": "Imam Nurhadi"
  }
}
```

## Not Found

```json
{
  "ok": false,
  "code": "CUSTOMER_NOT_FOUND",
  "data": null
}
```

## Rules

Tidak boleh menghasilkan:

```text
member_id = guessed value
```

Jika tidak ditemukan:

```text
ASK
OR
HANDOVER
```

# 10. Product Resolution Rules

```text
0 match
→ PRODUCT_NOT_FOUND

1 match
→ PRODUCT_RESOLVED

>1 match
→ PRODUCT_AMBIGUOUS
```

```json

  "sku_code": "SKU-009",

  "currency": "IDR"

```

| Field | Type | Required | Source |
|---|---|---:|---|
| `sku_code` | string | Yes | Product Master |
| `selling_price` | integer/decimal | Yes | Price Master |
| `currency` | string | Yes | Price Service |
| `service_fee` | integer/decimal | Business-rule dependent | Service/Rule |

Semua nilai harga menggunakan IDR sesuai data transaksi yang dianalisis.

# 12. Price Rules

1. Harga harus berasal dari Price Master/source of truth.
2. Agent tidak boleh mengarang harga.
3. Historical price bukan otomatis current price.
4. Jika price tidak tersedia:

```text
PRICE_UNAVAILABLE
```

5. Jika customer memberikan harga sendiri, harga customer hanya menjadi informasi yang perlu diverifikasi.

# 18. Order Draft Rules

Draft:

```text
CAN CHANGE
CAN CANCEL
CAN BE REVALIDATED
IS NOT A TRANSACTION
DOES NOT DEDUCT STOCK BY DEFAULT
```

# 24. Transaction Line Rule

One transaction:

```text
1 transaction_id
```

can have many lines:

```text
TRX-001 | SKU-A
TRX-001 | SKU-B
TRX-001 | SKU-C
```

One line:

```text
1 row = 1 SKU
```

Do not combine multiple SKU into one row.

---

# 25. Transaction ID Contract

Recommended format from existing documentation:

```text
TRX-YYYYMMDD-NNN
```

Example:

```text
TRX-20260824-001
```

Rules:

- unique;
- generated by system/transaction service;
- not generated by LLM;
- one transaction can contain multiple rows.

If a different production ID strategy is already used by Goodang backend, use the backend contract instead.

---

# 26. Transaction Date Contract

`transaction_date` means:

```text
date customer transaction occurred
```

It is not:

```text
created_at
```

Example:

```text
transaction_date = 2026-08-24
created_at = 2026-08-25 10:30:00
```

allowed if the transaction happened on August 24 and was entered on August 25.

---

# 27. Created At Contract

`created_at` means:

```text
when the record was created
```

Recommended:

```text
YYYY-MM-DD HH:MM:SS
```

Prefer system-generated timestamp.

---

# 28. Created By Contract

`created_by` represents the authenticated operator/system actor that created the record.

Recommended actor values may include:

```text
CS_USERNAME
AI_AGENT
SYSTEM
```

The final allowed values must be defined by Goodang authorization design.

Do not let the customer choose `created_by`.

---

# 29. Remarks Contract

Optional.

Use for information that cannot be represented by a dedicated field.

Examples:

```text
Kirim ke kantin
Pesanan acara sekolah
Customer meminta pengiriman sore
```

Do not use remarks as a replacement for:

```text
member_id
sku_code
qty
price
payment_method
```

---

# 30. Cooked Qty Contract

`cooked_qty` exists in the current transaction structure.

The available documentation does not establish a universal business formula for this field.

Therefore:

```text
Default for workflows not using cooked/prepared process:
0
```

until Goodang defines another rule.

Do not infer cooked quantity from customer text.

---

# 31. Service Fee Contract

`service_fee` exists in `POS_TRANSACTION_LOG`.

The current source does not establish a single universal formula for whether the fee is:

```text
per unit
per line
per transaction
```

Therefore:

```text
SERVICE_FEE_RULE = BUSINESS_RULE / TBD
```

Agent must retrieve the applicable rule/result from an authoritative service or configured business rule.

Never guess.

---

# 32. Line Amount Contract

Formula:

```text
line_amount = qty × selling_price
```

Example:

```text
qty = 2
selling_price = 79000

line_amount = 158000
```

`line_amount` is:

```text
line total for one SKU row
```

not total transaction value across all rows.

---

# 33. Total Order Contract

Recommended base:

```text
subtotal = SUM(line_amount)
```

Then:

```text
total = subtotal + applicable service fee
```

The exact service-fee aggregation must follow Goodang's business rule.

Do not infer a service-fee formula from historical records.

---

# 34. Payment Method Contract

Payment method must come from allowed values maintained by Goodang.

Example currently observed:

```text
PLAFON
```

Do not normalize free-text customer values blindly.

Example:

```text
"plafon"
"PLAFOND"
"credit"
"kredit"
```

must be mapped only if the payment master explicitly permits that mapping.

---

# 35. UOM Contract

UOM must come from Product Master.

Examples observed in the transaction documentation:

```text
Pcs
Bungkus
Kg
Renceng
Botol
Pack
Pouch
```

Agent must not invent a UOM.

Customer language may differ from master language.

Example:

```text
Customer:
"2 botol"

Master:
uom = Pcs
```

Do not change master UOM based on customer wording.

---

# 36. JSON Serialization Rules

Across API/tool boundaries:

- monetary values should be numeric;
- quantity should be numeric;
- IDs should be strings;
- nullable text should use `null`;
- timestamps should use a defined ISO-compatible format;
- enums should use canonical values;
- do not pass localized currency strings as numeric fields.

Good:

```json
{
  "selling_price": 79000,
  "qty": 2
}
```

Avoid:

```json
{
  "selling_price": "Rp79.000",
  "qty": "2 pcs"
}
```

---

# 38. Data Validation Order

For an order item:

```text
1. Identify customer
2. Resolve product
3. Validate quantity
4. Retrieve price
5. Check stock
6. Resolve payment
7. Calculate line amount
8. Build draft
9. Confirm
10. Transaction
11. Stock mutation
```

---

# 39. Cross-Field Validation

Examples:

```text
member_id must correspond to member_name
sku_code must correspond to product_name
sku_code must correspond to uom
qty > 0
selling_price >= 0
service_fee >= 0
line_amount = qty × selling_price
transaction_id consistent across transaction lines
```

If validation fails:

```text
DO NOT COMPLETE TRANSACTION
```

# 43. Data Contract Between ADK and Temporal

ADK sends intent/command:

```json
{
  "action": "CONFIRM_ORDER",
  "order_id": "DRAFT-001",
  "confirmed": true
}
```

Temporal does not blindly trust this as a completed transaction.

Temporal validates:

```text
draft
customer
product
price
stock
payment
confirmation
```

then executes the appropriate workflow.

---

# 44. Data Contract Between Temporal and Backend

Temporal Activity input:

```json
{
  "order_id": "DRAFT-001",
  "idempotency_key": "GOODANG:DRAFT-001"
}
```

Backend response:

```json
{
  "ok": true,
  "code": "TRANSACTION_CREATED",
  "data": {
    "transaction_id": "TRX-20260826-001"
  }
}
```

Temporal then executes stock/payment activities according to workflow.

# 45. Data Contract Between Transaction Service and `POS_TRANSACTION_LOG`

Transaction Service must transform:

```text
Confirmed Order
```

into:

```text
1 row per SKU
```

Example:

```text
Order:
Aqua 10
Indomie 5
Kopi 2
```

Output:

```text
TRX-001 | Aqua | 10
TRX-001 | Indomie | 5
TRX-001 | Kopi | 2
```

The Transaction Service owns this mapping.

# 46. Data Integrity Rules

Never create a final transaction if:

```text
member_id unknown
SKU unknown
price unknown
stock unknown
payment eligibility unknown
customer not confirmed
```

Never allow:

```text
negative qty
negative price
negative service_fee
line_amount mismatch
unknown SKU
unknown member
duplicate transaction side effect
```

---

# 47. Master Data Precedence

If customer text conflicts with master data:

```text
MASTER DATA
    >
CUSTOMER TEXT
```

Example:

Customer:

> "Beras Rojo Lele harganya 70 ribu."

Price Master:

```text
79000
```

Use:

```text
79000
```

and inform customer if relevant.

Do not silently use the customer's price.

---

# 48. Historical Data Precedence

Historical transaction data may be used for:

```text
reorder assistance
conversation context
customer preference
```

but not as the authoritative source for:

```text
current price
current stock
current payment limit
current product status
```

Those must use current services/master data.

# 52. Canonical Enum Rules

Do not allow arbitrary status strings where an enum is appropriate.

Daftar kanonik state, error code, dan event name didefinisikan di `docs/0. GOODANG_CONTRACT.md` (§2 state, §6 event, §7 error code). Enum di bawah adalah contoh untuk kontrak data — versi otoritatif ada di `docs/0`.

Example:

```text
Order Status (lihat docs/0 §2 untuk daftar lengkap 19 state):
NEW
BUILDING_ORDER
WAITING_CONFIRMATION
CONFIRMED
PROCESSING
COMPLETED
CANCELLED
HANDOVER_CS
ERROR
```

Example:

```text
Product Resolution:
PRODUCT_FOUND
PRODUCT_AMBIGUOUS
PRODUCT_NOT_FOUND
```

Example:

```text
Stock:
STOCK_AVAILABLE
INSUFFICIENT_STOCK
STOCK_UNAVAILABLE
```

The production implementation may extend the enum, but should not silently rename values.
