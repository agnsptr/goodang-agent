# GOODANG STATE MACHINE

**Project:** Goodang  
**Component:** Order State Machine  
**Channel:** Telegram  
**Agent Framework:** Google Agent Development Kit (ADK)  
**Workflow Engine:** Temporal  
**Primary Process:** CS Goodang — Guru Ingin Pesan  
**Primary Transaction Log:** `POS_TRANSACTION_LOG`  
**Document Type:** State Machine Contract  
**Version:** 1.0  
**Status:** Development Baseline

> **Canonical Contract:** Daftar kanonik 19 state name didefinisikan di `docs/0. GOODANG_CONTRACT.md` §2 (Single Source of Truth). Dokumen ini adalah SoT untuk **state transition** (trigger, guard, actor per transisi). Jika ada konflik nama state, `docs/0` menang.

---

# 1. Purpose

Dokumen ini mendefinisikan state machine resmi untuk proses order Goodang.

State machine menjadi kontrak antara:

```text
ADK Agent
      ↓
Application / Tool Layer
      ↓
Temporal Workflow
      ↓
Goodang Backend
```

Tujuan:

1. setiap order selalu memiliki state yang jelas;
2. setiap event hanya boleh menyebabkan transition yang diizinkan;
3. ADK tidak dapat melompati state transaksi;
4. transaction final hanya dapat dibuat dari state yang sah;
5. error dan timeout memiliki jalur yang jelas;
6. perubahan order dapat ditelusuri;
7. workflow dapat dipulihkan tanpa kehilangan state.

---

# 2. Authority

Temporal adalah **authority untuk Workflow State**.

ADK hanya menghasilkan:

```text
intent
structured command
customer response
```

ADK tidak boleh menetapkan state final secara sepihak.

Contoh:

```text
ADK:
"Customer sudah setuju."
```

Temporal tetap harus memverifikasi:

```text
current_state == WAITING_CONFIRMATION
```

sebelum transition:

```text
WAITING_CONFIRMATION
→ CONFIRMED
```

# 3. State Categories

Daftar kanonik 19 state name didefinisikan di `docs/0. GOODANG_CONTRACT.md` §2 (Single Source of Truth). Dokumen ini (docs/6) adalah SoT untuk **transisi** antar state. Kategori di bawah adalah pengelompokan untuk navigasi; nama resmi ada di `docs/0`.

State dibagi menjadi:

### Conversation / Preparation

```text
NEW
IDENTIFYING_CUSTOMER
BUILDING_ORDER
NEED_PRODUCT_CONFIRMATION
VALIDATING_ORDER
```

### Validation

```text
CHECKING_STOCK
CHECKING_PRICE
CHECKING_PAYMENT
```

### Customer Decision

```text
WAITING_CONFIRMATION
MODIFICATION_REQUESTED
```

### Execution

```text
CONFIRMED
PROCESSING
CREATING_TRANSACTION
UPDATING_STOCK
```

### Terminal

```text
COMPLETED
CANCELLED
HANDOVER_CS
ERROR
```

Optional future states:

```text
EXPIRED
PAYMENT_PENDING
STOCK_RESERVED
RELEASING_STOCK
REFUND_PENDING
```

State optional tidak boleh digunakan sebelum business rule ditetapkan.

# 4. State Definitions

| State | Meaning | Transaction Allowed? | Stock Mutation? |
|---|---|---:|---:|
| `NEW` | Order workflow baru dimulai | No | No |
| `IDENTIFYING_CUSTOMER` | Identifikasi customer | No | No |
| `BUILDING_ORDER` | Menyusun/mengubah draft | No | No |
| `NEED_PRODUCT_CONFIRMATION` | Produk ambigu/belum jelas | No | No |
| `VALIDATING_ORDER` | Memvalidasi draft | No | No |
| `CHECKING_STOCK` | Mengecek stok | No | No |
| `CHECKING_PRICE` | Mengecek harga | No | No |
| `CHECKING_PAYMENT` | Mengecek pembayaran | No | No |
| `WAITING_CONFIRMATION` | Menunggu persetujuan customer | No | No |
| `MODIFICATION_REQUESTED` | Customer meminta perubahan | No | No |
| `CONFIRMED` | Customer telah menyetujui | Yes, controlled | No |
| `PROCESSING` | Proses final sedang berjalan | Controlled | Controlled |
| `CREATING_TRANSACTION` | Transaction sedang dibuat | Yes | No |
| `UPDATING_STOCK` | Stock update sedang dilakukan | Already created | Yes |
| `COMPLETED` | Order selesai | N/A | Already done |
| `CANCELLED` | Order dibatalkan | No | No* |
| `HANDOVER_CS` | Menunggu intervensi manusia | No | No |
| `ERROR` | Error unrecoverable / membutuhkan handling | No | No |

`CANCELLED` tidak boleh menyebabkan stock release kecuali Goodang nantinya menggunakan stock reservation.

# 5. State Invariants

Invariant berikut harus selalu benar:

## INV-001

```text
state != CONFIRMED
→ transaction must not be created
```

## INV-002

```text
state != UPDATING_STOCK
→ no stock deduction operation
```

## INV-003

```text
WAITING_CONFIRMATION
→ customer confirmation is required
```

## INV-004

```text
COMPLETED
→ transaction_id must exist
```

## INV-005

```text
CANCELLED before transaction
→ transaction_id must be null
```

## INV-006

```text
transaction_id exists
→ transaction is final or processing
```

## INV-007

```text
stock deduction success
→ must reference a transaction_id
```

## INV-008

```text
order modifications
→ only allowed before final transaction
```

## Allowed Events

```text
INITIAL_MESSAGE
```

## Guard

```text
initial_message exists

```

## Action

```text
store initial message
```

## Next

```text

```

# 9. `IDENTIFYING_CUSTOMER`

## Event

```text
CUSTOMER_IDENTIFIED
```

## Guard

```text
member_id exists
member_name exists
customer status valid
```

## Next

```text
BUILDING_ORDER
```

---

## Customer Not Found

Event:

```text
CUSTOMER_NOT_FOUND
```

Next:

```text
HANDOVER_CS
```

or remain in:

```text
IDENTIFYING_CUSTOMER
```

while waiting for additional information.

Business policy determines which path applies.

---

# 10. `BUILDING_ORDER`

Purpose:

```text
create order draft
add item
remove item
update item
```

Allowed events:

```text
ADD_ITEM
UPDATE_ITEM
REMOVE_ITEM
ORDER_DATA_READY
PRODUCT_AMBIGUOUS
```

Transitions:

```text
ADD_ITEM
→ BUILDING_ORDER

UPDATE_ITEM
→ BUILDING_ORDER

REMOVE_ITEM
→ BUILDING_ORDER

PRODUCT_AMBIGUOUS
→ NEED_PRODUCT_CONFIRMATION

ORDER_DATA_READY
→ VALIDATING_ORDER
```

Purpose:

Menunggu customer memilih produk yang ambigu.

Example:

```text
Aqua 600ML
Aqua 1500ML
Aqua Galon
```

Event:

```text
PRODUCT_SELECTED
```

Guard:

```text
exact SKU identified
```

Next:

```text
BUILDING_ORDER
```

Event:

```text
CUSTOMER_CANCEL
```

Next:

```text
CANCELLED
```

# 12. `VALIDATING_ORDER`

Checks:

```text
customer
product
quantity
UOM
price
payment
order structure
```

Possible events:

```text
ORDER_VALID
ORDER_INVALID
```

If valid:

```text
CHECKING_STOCK
```

If invalid:

```text
BUILDING_ORDER
```

If information cannot be resolved:

```text
NEED_PRODUCT_CONFIRMATION
```

or:

```text
HANDOVER_CS
```

# 13. `CHECKING_STOCK`

Activity:

```text
check_stock()
```

## Success

```text
STOCK_AVAILABLE
```

Next:

```text
CHECKING_PRICE
```

## Insufficient

```text
INSUFFICIENT_STOCK
```

Next:

```text
BUILDING_ORDER
```

Customer must choose:

```text
reduce quantity
replace product
remove product
cancel
```

## Technical Error

```text
STOCK_SERVICE_UNAVAILABLE
```

Action:

```text
retry activity
```

If retry exhausted:

```text
HANDOVER_CS
```

or:

```text
ERROR
```

---

# 14. `CHECKING_PRICE`

Activity:

```text
get_price()
```

## Success

```text
PRICE_FOUND
```

Next:

```text
CHECKING_PAYMENT
```

## Price Missing

```text
PRICE_NOT_FOUND
PRICE_UNAVAILABLE
```

Next:

```text
HANDOVER_CS
```

or return to customer clarification.

## Price Mismatch

```text
PRICE_MISMATCH
```

Next:

```text
HANDOVER_CS
```

unless business policy explicitly allows customer confirmation of the current price.

```text
PAYMENT_VALID
```

Next:

```text
WAITING_CONFIRMATION
```

## Insufficient

```text
INSUFFICIENT_PAYMENT_LIMIT
```

Next:


# 16. `WAITING_CONFIRMATION`

This is the **transaction gate**.

Allowed events:

```text
CUSTOMER_CONFIRM
CUSTOMER_MODIFY
CUSTOMER_CANCEL
```

## Confirm

Guard:

```text
all validation statuses are valid
```

Next:

```text
CONFIRMED
```

## Modify

Next:

```text
MODIFICATION_REQUESTED
```

## Cancel

Next:

```text
CANCELLED
```

No final transaction may be created while in this state.

---

# 17. `MODIFICATION_REQUESTED`

Purpose:

Capture customer changes.

Examples:

```text
"Indomie jadi 5"
"Tambah minyak 2"
"Batal kopi"
```

Action:

```text
load active draft
interpret modification
apply draft change
```

Next:

```text
BUILDING_ORDER
```

Then the order must be revalidated.

---

# 18. Confirmation Semantic Guard

Important:

```text
"YA"
```

is only a confirmation if:

```text
current_state == WAITING_CONFIRMATION
```

Example:

```text
State:
NEED_PRODUCT_CONFIRMATION

Customer:
"Ya"
```

Must NOT transition to:

```text
CONFIRMED
```

It remains waiting for product selection.

---

# 19. `CONFIRMED`

Entry means:

```text
customer confirmation accepted
```

Preconditions:

```text
draft valid
customer valid
product valid
quantity valid
stock valid
price valid
payment valid
customer_confirmed = true
```

Next:

```text
PROCESSING
```

No customer order modification should be accepted as a normal draft update after entering this state.

---

# 20. `PROCESSING`

This is the final execution zone.

Possible transitions:

```text
CREATING_TRANSACTION
```

Then:

```text
UPDATING_STOCK
```

Then:

```text
COMPLETED
```

Technical failure:

```text
RETRY
```

Permanent/business failure:

```text
ERROR
```

or:

```text
HANDOVER_CS
```

---

# 21. `CREATING_TRANSACTION`

Activity:

```text
create_transaction()
```

Required idempotency:

```text
GOODANG:{order_id}
```

## Success

```text
TRANSACTION_CREATED
```

Store:

```text
transaction_id
```

Next:

```text
UPDATING_STOCK
```

## Already Exists

```text
TRANSACTION_ALREADY_EXISTS
```

Return existing:

```text
transaction_id
```

Then:

```text
UPDATING_STOCK
```

## Failure

Retry technical failure.

Do not create a new order.

---

# 22. `UPDATING_STOCK`

Activity:

```text
deduct_stock()
```

Required idempotency:

```text
GOODANG-STOCK:{transaction_id}
```

## Success

```text
STOCK_DEDUCTED
```

Next:

```text
COMPLETED
```

## Already Deducted

```text
STOCK_ALREADY_DEDUCTED
```

Next:

```text
COMPLETED
```

## Failure

Retry technical failure.

If retries exhausted:

```text
ERROR
```

or:

```text
HANDOVER_CS
```

Business reconciliation is required before claiming completion.

---

# 23. `COMPLETED`

Terminal state.

Required:

```text
transaction_id exists
transaction created successfully
stock update completed
```

Customer response:

> "Pesanan berhasil dibuat."

Optional:

```text
transaction_id
total
payment_method
```

No standard modification allowed.

---

# 24. `CANCELLED`

Terminal state for unfinalized order.

Required:

```text
no final transaction created
```

Customer response:

> "Pesanan dibatalkan."

Do not delete draft history from audit logs.

---

# 25. `HANDOVER_CS`

Non-terminal operational state.

Required context:

```text
order_id
member_id
chat_id
current draft
current state
reason
last customer message
```

Human CS may resolve and resume workflow.

Example:

```text
HANDOVER_CS
      ↓
HUMAN_RESOLUTION
      ↓
BUILDING_ORDER
```

or:

```text
HANDOVER_CS
      ↓
HUMAN_CONFIRMATION
      ↓
CONFIRMED
```

Exact resume transition must be authorized.

---

# 26. `ERROR`

Used when automated workflow cannot continue safely.

Examples:

```text
unrecoverable infrastructure failure
data corruption
transaction reconciliation failure
unknown workflow state
```

Customer response must not falsely claim success.

Recommended:

> "Pesanan belum dapat diproses karena terjadi kendala sistem. CS akan membantu melanjutkannya."

# 29. Illegal Transition Rules

Any transition not defined in this document is:

```text
INVALID_TRANSITION
```

Examples:

```text
NEW
→ COMPLETED
```

invalid.

```text
WAITING_CONFIRMATION
→ UPDATING_STOCK
```

invalid.

```text
BUILDING_ORDER
→ COMPLETED
```

invalid.

```text
CHECKING_STOCK
→ TRANSACTION_CREATED
```

invalid.

# 30. Final Transaction Gate

The only legal path to transaction creation is:

```text
BUILDING_ORDER
      ↓
VALIDATING_ORDER
      ↓
CHECKING_STOCK
      ↓
CHECKING_PRICE
      ↓
CHECKING_PAYMENT
      ↓
WAITING_CONFIRMATION
      ↓
CUSTOMER_CONFIRM
      ↓
CONFIRMED
      ↓
PROCESSING
      ↓
CREATING_TRANSACTION
```

No alternate path may bypass confirmation.

---

# 31. Final Completion Gate

The only legal path to `COMPLETED` is:

```text
CONFIRMED
      ↓
PROCESSING
      ↓
CREATING_TRANSACTION
      ↓
TRANSACTION_CREATED
      ↓
UPDATING_STOCK
      ↓
STOCK_DEDUCTED
      ↓
COMPLETED
```

If Goodang later introduces a different payment/stock architecture, this path must be versioned and updated formally.

```text
WAITING_CONFIRMATION
        │
        │ MODIFY
        ▼
MODIFICATION_REQUESTED
        │
        ▼
BUILDING_ORDER
        │
        ▼
VALIDATING_ORDER
        │
        ▼
CHECKING_STOCK
        │
        ▼
CHECKING_PRICE
        │
        ▼
CHECKING_PAYMENT
        │
        ▼
WAITING_CONFIRMATION
```

---

# 33. Cancellation Loop

Before confirmation:

```text
ANY PRE-CONFIRMATION STATE
        │
        │ CANCEL
        ▼
CANCELLED
```

Exception:

If the system has a stock reservation mechanism, cancellation may require:

```text
CANCELLED
   ↓
RELEASE_STOCK
```

This is future behavior and requires an explicit reservation policy.

# 38. Concurrency Rules

The system must avoid conflicting modifications to the same order.

Example:

```text
Customer message A:
"Indomie jadi 5"

Customer message B:
"Tambah minyak 2"
```

The workflow must process events in a deterministic order.

Do not allow two independent transaction mutations to race against the same draft.

---

# 39. Duplicate Event Rules

Duplicate:

```text
CUSTOMER_CONFIRM
```

must not create multiple transactions.

Duplicate:

```text
STOCK_DEDUCT
```

must not deduct twice.

Duplicate:

```text
TELEGRAM_UPDATE
```

must not create duplicate business actions.

---

# 40. Timeout Rules

State-specific timeouts may be introduced later.

Example:

```text
WAITING_CONFIRMATION
    ↓
business timeout
    ↓
EXPIRED
```

The exact timeout is `TBD` until Goodang defines the business policy.

Technical Activity timeout is different from business order expiration.

# 41. Retry Rules by State

| State | Retry |
|---|---|
| `IDENTIFYING_CUSTOMER` | Technical Activity errors only |
| `CHECKING_STOCK` | Technical errors |
| `CHECKING_PRICE` | Technical errors |
| `CHECKING_PAYMENT` | Technical errors |
| `CREATING_TRANSACTION` | Technical errors, idempotent |
| `UPDATING_STOCK` | Technical errors, idempotent |
| Customer clarification | No automatic retry |
| Business invalid state | No blind retry |

---

# 42. State Recovery

After worker restart:

```text
persisted Temporal state
        ↓
resume current state
        ↓
continue from durable execution point
```

Examples:

```text
WAITING_CONFIRMATION
→ continue waiting

CREATING_TRANSACTION
→ use idempotency on retry

UPDATING_STOCK
→ use transaction_id idempotency
```

Do not recreate the workflow from the first Telegram message.

| Current | Event | Guard | Next |
|---|---|---|---|
| `NEW` | `INITIAL_MESSAGE` | input valid | `IDENTIFYING_CUSTOMER` |

# 44. Illegal Commands

Commands must be rejected when the state is incompatible.

Example:

```text
confirm_order()
```

while:

```text
state = BUILDING_ORDER
```

must return:

```text
CONFIRMATION_REQUIRED
```

or:

```text
ORDER_NOT_READY
```

Do not force the state to `CONFIRMED`.

# 46. Acceptance Criteria

State machine dianggap benar jika:

- [ ] setiap state memiliki definisi;
- [ ] setiap valid transition terdokumentasi;
- [ ] illegal transition ditolak;
- [ ] confirmation gate enforced;
- [ ] transaction hanya berasal dari confirmed flow;
- [ ] stock mutation hanya berasal dari authorized execution;
- [ ] cancellation tidak membuat transaction;
- [ ] modification kembali ke validation;
- [ ] ambiguous product tidak bypass;
- [ ] duplicate events aman;
- [ ] worker restart aman;
- [ ] transaction retry aman;
- [ ] state audit tersedia.

---

# 47. Implementation Guidance

Temporal Workflow harus menjadi implementasi state machine ini.

ADK tidak boleh mengimplementasikan second competing state machine yang memiliki aturan berbeda.

Recommended:

```text
ADK
 ↓
intent / command
 ↓
Temporal Workflow
 ↓
state guard
 ↓
Activity
 ↓
result
 ↓
next state
```

Satu authoritative state machine:

```text
TEMPORAL
```

# 48. Versioning

Perubahan pada:

```text
state
transition
guard
transaction path
stock path
payment path
```

harus dianggap perubahan workflow contract.

Sebelum deploy perubahan:

```text
review
→ compatibility check
→ migration/versioning strategy
→ test
→ deploy
```

Jangan mengubah state workflow aktif secara sembrono.

# 50. Non-Negotiable Rules

```text
1. Temporal owns workflow state.
2. ADK cannot force a state transition.
3. Every transition requires a valid event and guard.
4. No transaction before customer confirmation.
5. No transaction from an invalid state.
6. No stock deduction during draft.
7. No completion before transaction and stock success.
8. No ambiguous product may reach transaction.
9. Duplicate commands must be idempotent.
10. Worker restart must preserve state.
11. Technical retry must not create duplicate side effects.
12. Historical transactions must not be silently modified.
13. Unknown transitions must fail closed.
14. State changes must be auditable.
15. Business rules not defined in this document remain TBD.
```
