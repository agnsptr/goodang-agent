# GOODANG TEMPORAL WORKFLOW SPEC

**Project:** Goodang  
**Component:** Temporal Business Workflow Layer  
**Channel:** Telegram  
**Agent Framework:** Google Agent Development Kit (ADK)  
**Workflow Engine:** Temporal  
**Primary Business Process:** CS Goodang — Guru Ingin Pesan  
**Primary Transaction Log:** `POS_TRANSACTION_LOG`  
**Document Type:** Temporal Workflow Specification  
**Version:** 1.0  
**Status:** Development Baseline

---

# 1. Purpose

Dokumen ini mendefinisikan bagaimana SOP CS Goodang diterjemahkan menjadi **durable business workflow** menggunakan Temporal.

Temporal menjadi authority untuk:

```text
workflow state
durable execution
waiting
retry
timeout
recovery
transaction orchestration
stock orchestration
payment orchestration
idempotency boundary
```

ADK tetap bertanggung jawab terhadap:

```text
natural language understanding
intent detection
entity extraction
conversation
tool selection
customer-facing response
```

Goodang backend tetap menjadi source of truth:

```text
member
product
price
stock
payment
transaction
```

Temporal cocok untuk workflow transaksi dan order karena dirancang agar execution dapat dilanjutkan setelah crash, network failure, atau infrastructure outage. citeturn129284search0

---

# 2. Non-Goals

Workflow ini bukan:

- chatbot;
- LLM;
- database;
- Product Master;
- Stock Master;
- Payment Ledger;
- Transaction Ledger;
- Telegram server.

Temporal hanya mengorkestrasi proses menggunakan data dari source of truth.

# 6. Workflow Identity

For the initial Telegram implementation, recommended deterministic Workflow ID:

```text
goodang-order-{telegram_chat_id}
```

Example:

```text
goodang-order-123456789
```

This supports one active order conversation per Telegram chat.

If Goodang requires multiple simultaneous active orders per customer, use an explicit order ID:

```text
goodang-order-{member_id}-{order_id}
```

Do not create an arbitrary workflow ID per incoming Telegram message.

# 9. State Transition Rules

```text
NEW
 ↓
IDENTIFYING_CUSTOMER
 ↓
BUILDING_ORDER
 ↓
VALIDATING_ORDER
 ↓
CHECKING_STOCK
 ↓
CHECKING_PRICE
 ↓
CHECKING_PAYMENT
 ↓
WAITING_CONFIRMATION
```

From `WAITING_CONFIRMATION`:

```text
CONFIRM → CONFIRMED
MODIFY   → MODIFICATION_REQUESTED → BUILDING_ORDER
CANCEL   → CANCELLED
```

After confirmation:

```text
CONFIRMED
 ↓
PROCESSING
 ↓
CREATING_TRANSACTION
 ↓
UPDATING_STOCK
 ↓
COMPLETED
```

Exceptional:

```text
CUSTOMER_NOT_FOUND → HANDOVER_CS
PRODUCT_NOT_FOUND → NEED_PRODUCT_CONFIRMATION
PRODUCT_AMBIGUOUS → NEED_PRODUCT_CONFIRMATION
INSUFFICIENT_STOCK → BUILDING_ORDER / WAITING_CUSTOMER
PRICE_MISMATCH → HANDOVER_CS / CUSTOMER_CONFIRMATION
PAYMENT_INVALID → BUILDING_ORDER
SYSTEM_FAILURE → ERROR / RETRY / HANDOVER
```

# 10. State Authority Rule

Only Temporal Workflow may determine the authoritative business state.

ADK may recommend an action:

```json
{
  "action": "CONFIRM_ORDER",
  "order_id": "DRAFT-001"
}
```

but Temporal must verify:

```text
order exists
AND
order state = WAITING_CONFIRMATION
AND
customer confirmation is valid
```

before transition.

# 14. Product Identification

ADK interprets customer language.

Example:

```text
"beras 2"
```

ADK output:

```json
{
  "product_query": "beras",
  "qty": 2
}
```

Temporal/Application layer then calls:

```text
search_product()
```

Results:

```text
0 match → PRODUCT_NOT_FOUND
1 match → RESOLVED
>1 match → PRODUCT_AMBIGUOUS
```

---

# 15. Product Ambiguity

If multiple products match:

```text
NEED_PRODUCT_CONFIRMATION
```

Example:

```text
Aqua 600ML
Aqua 1500ML
Aqua Galon
```

Customer must select.

No order transaction can be finalized while the SKU is unresolved.


# 20. Order Draft Construction

After the necessary validation:

```text
BUILDING_ORDER
       ↓
DRAFT CREATED
       ↓
WAITING_CONFIRMATION
```

Draft structure:

```json
{
  "order_id": "DRAFT-001",
  "status": "WAITING_CONFIRMATION",
  "member_id": "MBR-050",
  "member_name": "Imam Nurhadi",
  "payment_method": "PLAFON",
  "items": [
    {
      "sku_code": "SKU-009",
      "product_name": "BERAS SUPER ROJO LELE 5KG",
      "uom": "Kg",
      "qty": 2,
      "selling_price": 79000,
      "service_fee": 0,
      "line_amount": 158000
    }
  ],
  "subtotal": 158000,
  "service_fee": 0,
  "total": 158000
}
```

---

# 21. Calculation

For each item:

```text
line_amount = qty × selling_price
```

Example:

```text
2 × 79000 = 158000
```

Order subtotal:

```text
subtotal = SUM(line_amount)
```

Total:

```text
total = subtotal + applicable service fee
```

Service fee calculation must follow the authoritative Goodang business rule.

Do not infer service fee calculation from historical transactions.


```text

```

AND:


```text

```

```text
       ↓
```

# 31. Transaction Execution

After:

```text
WAITING_CONFIRMATION
        ↓
customer confirmed
        ↓
CONFIRMED
```

Workflow enters:

```text
PROCESSING
```

Then:

```text
CREATING_TRANSACTION
```

Call:

```text
create_transaction
```

---

# 32. Transaction Preconditions

Before `create_transaction`:

```text
customer_valid == true
product_valid == true
price_valid == true
stock_valid == true
payment_valid == true
customer_confirmed == true
order_state == CONFIRMED
```

If any condition fails:

```text
TRANSACTION_NOT_ALLOWED
```

---

# 33. Transaction Idempotency

`create_transaction` must be idempotent.

Recommended key:

```text
GOODANG:{order_id}
```

Example:

```text
GOODANG:DRAFT-20260826-001
```

If the Activity is retried:

```text
existing transaction
      ↓
return existing transaction_id
```

Do not create a second transaction.

---

# 34. Transaction Result

Expected:

```json
{
  "ok": true,
  "code": "TRANSACTION_CREATED",
  "data": {
    "transaction_id": "TRX-20260826-001"
  }
}
```

Temporal stores:

```text
transaction_id
```

as part of workflow state.

---

# 35. POS_TRANSACTION_LOG

The Transaction Service must create one row per SKU.

Example:

```text
TRX-001 | SKU-009 | qty 2
TRX-001 | SKU-014 | qty 10
TRX-001 | SKU-206 | qty 5
```

The workflow must never append rows directly to `POS_TRANSACTION_LOG`.

---

# 36. Stock Deduction

After transaction creation succeeds:

```text
TRANSACTION_CREATED
       ↓
UPDATING_STOCK
       ↓
deduct_stock()
       ↓
COMPLETED
```

Recommended idempotency key:

```text
GOODANG-STOCK:{transaction_id}
```

If retry occurs, stock must not be deducted twice.

---

# 37. Atomicity Consideration

Do not assume that:

```text
create transaction
+
deduct stock
```

is a single database transaction if they are separate services.

Temporal should orchestrate the process.

If the first step succeeds and the second fails:

```text
TRANSACTION_CREATED
STOCK_UPDATE_FAILED
```

Workflow must retry/reconcile according to the defined business policy.

Do not silently create another transaction.

---

# 38. Payment Execution

If payment requires actual execution rather than eligibility check:

```text
CHECK_PAYMENT
       ↓
CUSTOMER_CONFIRMATION
       ↓
EXECUTE_PAYMENT
       ↓
CREATE_TRANSACTION
```

The exact ordering must follow the Goodang payment business rule.

Do not invent payment sequencing if backend requirements differ.

---

# 39. Failure Classification

## Retryable

Examples:

```text
network timeout
temporary service unavailable
HTTP 5xx
temporary infrastructure failure
```

Temporal should retry according to Activity RetryPolicy.

## Business Failure

Examples:

```text
CUSTOMER_NOT_FOUND
PRODUCT_NOT_FOUND
PRODUCT_AMBIGUOUS
INSUFFICIENT_STOCK
PRICE_MISMATCH
INSUFFICIENT_PAYMENT_LIMIT
ORDER_INVALID_STATE
```

Do not retry endlessly.

Return the business result to the workflow.

---

# 40. Activity Retry Policy

Recommended initial baseline:

```text
initial_interval = 2 seconds
backoff_coefficient = 2
maximum_interval = 30 seconds
maximum_attempts = 5
```

These values are initial engineering defaults, not business policy. Tune them using real service behavior.

---

# 41. Activity Timeout

Recommended initial baseline:

```text
read activities:
5–10 seconds

mutation activities:
10–30 seconds

transaction:
up to 30 seconds
```

Final timeout values must follow actual Goodang API SLA and behavior.

---

# 42. Workflow Determinism

Workflow code must remain deterministic.

Do not perform directly inside Workflow:

```textHTTP calls
database queries
random values
current system time outside Temporal APIs
filesystem access
environment-dependent side effects
```

Use Activities for external I/O and Temporal-provided deterministic APIs where applicable.

---

# 43. Workflow Waiting

When waiting for customer response:

```text
WAITING_CONFIRMATION
```

the Workflow must wait using Temporal's durable workflow primitives.

Do not implement:

```text
while true:
    sleep()
    poll telegram
```

as the primary customer confirmation mechanism.

Use Signal/Update or the appropriate Temporal interaction mechanism supported by the selected SDK.

---

# 46. Customer Success Response Guard

Only after:

```text
transaction success
AND
stock update success
```

may the customer receive:

> "Pesanan berhasil dibuat."

Before that:

> "Pesanan sedang diproses."

If final processing fails:

> "Pesanan belum dapat diselesaikan karena terjadi kendala pada sistem."

Do not expose stack trace or internal service names.

Future/optional behavior:

```text

       ↓

       ↓

```

---

# 54. Stock Reservation

Reservation is optional.

Current baseline:

```text
CHECK_STOCK
    ↓
WAIT_CONFIRMATION
    ↓
CREATE_TRANSACTION
    ↓
DEDUCT_STOCK
```

Do not introduce stock reservation unless Goodang explicitly requires it.

If reservation is later required:

```text
RESERVE_STOCK
    ↓
WAIT_CONFIRMATION
    ├── CONFIRM → COMMIT
    └── CANCEL  → RELEASE
```

Reservation needs its own timeout and compensation rules.

---

# 55. Compensation Strategy

Temporal is not a distributed database transaction.

If:

```text
Payment succeeds
Transaction fails
```

then workflow requires a business-defined compensation:

```text
REFUND
REVERSE_PAYMENT
RECONCILIATION
```

Do not invent compensation logic.

Mark:

```text
REQUIRES_BUSINESS_RULE
```

until Goodang defines it.

# 60. Workflow Versioning

When changing an already-running Workflow, consider Temporal Workflow versioning/patching strategy rather than silently deploying incompatible code.

Examples of risky changes:

```text
state name changes
activity contract changes
workflow branching changes
data structure changes
```

A workflow update must preserve compatibility with histories that are still executing.

```python
async def GoodangOrderWorkflow(input):

    state = NEW

    identify customer

    if not found:

        return

    while order_not_completed:

        if create order:
            resolve products
            validate quantities
            check stock
            get price
            check payment
            create/update draft
            ask confirmation

        if modify:
            update draft
            revalidate
            recalculate
            ask confirmation

        if cancel:
            cancel draft
            finish

        if confirm:

            create transaction
            update stock
            complete
```
