## 2. Topology Per Fase

### 2.1 Fase 1 — Foundation (MVP, <100 workflow/hari)

```text
Telegram
  ↓ (webhook, HTTPS)
Cloudflare Workers (edge, webhook receiver + secret validation)
  ↓ enqueue (HTTPS + service_role)
Supabase Project #1: goodang-app
  ├─ Postgres (app data: Member/Product/Stock/Price/Payment/Order/Draft/POS_TRANSACTION_LOG/Audit)
  ├─ Queue (pgmq: telegram_inbound)
  ├─ Auth (CS dashboard)
  └─ Realtime (push ke CS dashboard)
  ↓ dequeue (polling)
VPS-1 (4 vCPU / 8GB / Docker)
  ├─ Container: goodang-adk (webhook consumer + ADK agent + tool registry Class A/B/C)
  └─ Container: goodang-app-layer (FastAPI, tool implementation Class A/B/C)
VPS-2 (4 vCPU / 8GB / Docker)
  ├─ Container: temporal-server (frontend + history + matching)
  ├─ Container: goodang-temporal-worker (activity implementation Class D)
  └─ Container: postgres-temporal (dedicated DB)
Supabase Project #2: goodang-temporal (dedicated, atau Neon free tier)
  └─ Postgres (Temporal schema: temporal.visibility, temporal.execution)
```

### 2.2 Fase 3 — Adopsi (production, >1k workflow/hari)

```text
Telegram → Cloudflare Workers → Supabase Queue → ADK (Cloud Run / Fly.io autoscale)
                                                ↓
                                            Temporal Cloud (managed, SLA 99.9%)
                                                ↓ activities
                                            App Layer (Cloud Run) → Supabase HA (read replicas)
                                                                      ↓
                                                                  POS_TRANSACTION_LOG (append-only)
```

## 3. Supabase Project Layout

### 3.1 Project #1: `goodang-app` (app data)

| Item | Value |
|:--|:--|
| Region | ap-southeast-1 (Singapore) — terdekat ke Indonesia |
| Plan | Free (Fase 1) → Pro (Fase 3) |
| Postgres version | 15 |
| Connection pooler | pgBouncer (port 6543) untuk ADK & App Layer |
| Direct connection | port 5432 untuk Transaction Service (Class D) |
| PITR | Enabled (Pro) |
| Backups | Daily + 7-day retention |

**Schema:** `goodang` (bukan `public`) — memudahkan RLS scoping.

**Tables (lihat `docs/14. GOODANG_SUPABASE_SCHEMA_SPEC.md`):**
- `member`
- `product`
- `price`
- `stock`
- `payment`
- `payment_method`
- `order_draft`
- `pos_transaction_log` (append-only, locked)
- `audit_log`
- `agent_memory` (Hermes, Fase 4)
- `telegram_update_dedup` (idempotency)

**RLS:** enabled di semua table. Policy:
- `authenticated` (CS dashboard user): read-only via Supabase Auth
- `service_role` (backend): bypass RLS, used by App Layer & Transaction Service
- `anon`: deny all

### 3.2 Project #2: `goodang-temporal` (Temporal DB)

| Item | Value |
|:--|:--|
| Region | same as #1 |
| Plan | Free (Fase 1) → Pro (Fase 3) |
| Postgres version | 15 |
| Connection | direct (no pooler — Temporal butuh session mode) |
| PITR | Enabled |

**Schema:** `temporal` (default Temporal schema). Migration via `temporal-sql-tool setup-schema`.

**Aturan:**
- App Layer **tidak boleh** query ke project #2
- Hanya Temporal server + worker yang connect
- Backup terpisah dari project #1

## 5. Webhook Flow (Telegram → ADK)

### 5.1 Sequence

```text
1. Customer kirim message ke Telegram Bot
2. Telegram push webhook ke Cloudflare Workers URL (HTTPS)
3. Cloudflare Workers:
   a. Validate X-Telegram-Bot-Api-Secret-Token (constant-time compare)
   b. Parse update, extract telegram_update_id, chat_id, user_id, text
   c. INSERT ke telegram_update_dedup (unique telegram_update_id)
      - Kalau conflict → duplicate, ack 200 ke Telegram (idempotent)
   d. Enqueue ke pgmq.telegram_inbound
   e. Return 200 ke Telegram (hanya setelah enqueue berhasil)
4. ADK worker (VPS-1) polling pgmq.telegram_inbound:
   a. SELECT pgmq.read('telegram_inbound', 30, 1) — visibility 30s
   b. Process via ADK agent
   c. ADK call tools (Class A/B/C) via App Layer
   d. ADK send Signal/Update ke Temporal workflow (Class C)
   e. ADK send response ke Telegram via send_telegram_message_activity
   f. pgmq.ack('telegram_inbound', msg_id)
5. Kalau ADK crash sebelum ack → message balik ke queue setelah 30s → retry
```

### 5.2 Cloudflare Workers contract

- Runtime: Cloudflare Workers (V8 isolate, zero cold start)
- Secrets: `TELEGRAM_BOT_SECRET`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (untuk enqueue + dedup insert)
- Rate limit: 100 req/sec per chat_id (anti-spam)
- Timeout: 30s (Telegram timeout)
- Error handling: kalau Supabase down, return 500 ke Telegram → Telegram retry

### 5.3 Idempotency

- `telegram_update_id` unique constraint di `telegram_update_dedup` table
- Duplicate webhook (Telegram retry) → INSERT conflict → ack 200, skip
- ADK processing idempotent via Temporal workflow ID (`GOODANG:{order_id}`)

## 6. Observability Stack

### 6.1 OpenTelemetry Pipeline

```text
ADK ──┐
App Layer ──┤
Temporal Worker ──┤── OTel Collector ──┬── Tempo (traces)
Postgres ──┘                          ├── Loki (logs)
                                      └── Prometheus (metrics)
Grafana (dashboard, alerting)
```

### 6.2 Metrics (wajib expose)

| Metric | Type | Labels |
|:--|:--|:--|
| `adk_intent_classification_total` | counter | `intent`, `outcome` |
| `adk_tool_call_duration_seconds` | histogram | `tool_name`, `class` |
| `temporal_workflow_duration_seconds` | histogram | `workflow_type`, `final_state` |
| `temporal_activity_retry_total` | counter | `activity_type`, `error_code` |
| `supabase_query_duration_seconds` | histogram | `table`, `operation` |
| `pos_transaction_log_writes_total` | counter | `outcome` |
| `telegram_webhook_received_total` | counter | `source` |
| `queue_lag_seconds` | gauge | `queue_name` |

### 6.3 Alerts

| Alert | Condition | Severity |
|:--|:--|:--|
| Handover rate spike | `HANDOVER_CS` rate > 5% dalam 1 jam | P2 — page CS lead |
| Activity retry spike | `temporal_activity_retry_total` p95 > 3 | P1 — page DevOps |
| Payment failure spike | `PAYMENT_FAILED` rate > 2% | P1 — page Finance + DevOps |
| Queue lag | `queue_lag_seconds` > 60 | P1 — page DevOps |
| POS_TRANSACTION_LOG mutation attempt | trigger `FORBID_ROW_MODIFICATION` fired | P0 — page Security |

### 6.4 PII Masking

Wajib di log layer (OTel processor):
- `member_name` → `***`
- `phone_number` → `***`
- `chat_id` → hash SHA256 truncated
- `payment_method` detail → `***`

## 8. Security Checklist Fase 1

- [ ] Telegram webhook secret validation (constant-time compare)
- [ ] Supabase RLS enabled di semua table
- [ ] `service_role` key hanya di `goodang-temporal-worker` (tidak di ADK, tidak di Cloudflare Workers untuk app data — Workers pakai service_role hanya untuk enqueue + dedup, dengan insert-only policy)
- [ ] `POS_TRANSACTION_LOG` append-only trigger aktif
- [ ] WireGuard / private network antar VPS
- [ ] UFW: hanya 443 (webhook), 22 (SSH key-only)
- [ ] Temporal gRPC (7233) internal-only, tidak expose ke internet
- [ ] Temporal UI (8233) behind basic auth + IP allowlist
- [ ] OTel PII masking aktif
- [ ] Backup PITR tested (restore drill)
- [ ] Secret rotation: Supabase JWT quarterly, Temporal mTLS 90 hari
