## 0. Cara Pakai Dokumen Ini

Dokumen ini adalah **authority tertinggi** untuk:

- nama state,
- nama tool,
- nama activity,
- nama event,
- error/result code,
- idempotency key format,
- confirmation keyword mapping,
- schema field contract,
- timeout & retry policy.

Setiap dokumen lain (`docs/1`–`docs/11`, `docs/GOODANG_ADK_PROMPT_SPEC.md`) **wajib referensi** ke dokumen ini dan **tidak boleh mendefinisikan ulang**. Jika ada konflik antara dokumen lain dan dokumen ini, dokumen ini menang.

Dokumen ini **bukan** pengganti dokumen detail. Dokumen ini hanya mendefinisikan **nama dan kontrak kanonik**. Detail alur, implementasi, dan contoh tetap di dokumen masing-masing (lihat §12 SoT Mapping).

## 1. Authority & Hierarchy

Jika terdapat konflik antara instruction, conversation, dan data, gunakan urutan:

```
1. System / Safety Rules
2. Goodang Business Rules
3. SOP
4. Temporal Workflow State
5. Source-of-Truth Data
6. Customer Context
7. LLM Reasoning
```

LLM reasoning tidak boleh mengalahkan aturan pada level di atas.

Final principles:

```
AI understands.
System validates.
Temporal executes.
Database records.
Chat != Order != Transaction
No Guessing. No Bypass. No Direct DB Mutation. No Transaction Without Confirmation.
```

```

### 2.2 Terminal states

```
CANCELLED

```

### 2.3 Optional state (TBD business rule)

```
EXPIRED       ← triggered when WAITING_CONFIRMATION melebihi 30 menit (lihat §11)
```

### 2.4 Ghost states — DILARANG

State berikut **tidak boleh dipakai** dan harus dihapus dari semua dokumen:

```
WAITING_CUSTOMER        ❌ (gunakan BUILDING_ORDER atau WAITING_CONFIRMATION)
CUSTOMER_CONFIRMATION   ❌ (gunakan WAITING_CONFIRMATION)
VALIDATION              ❌ (gunakan VALIDATING_ORDER)
```

### 2.5 State transition authority

Temporal adalah **authority untuk Workflow State**. ADK hanya menghasilkan intent, structured command, dan customer response. ADK tidak boleh menetapkan state final sepihak.

Detail transisi (trigger, guard, actor) ada di `docs/6. GOODANG_STATE_MACHINE.md`. Dokumen ini hanya mendefinisikan nama state.

## 4. Canonical Temporal Activity Names (SoT)

Konvensi: `<tool_name>_activity`. Setiap activity membungkus tepat satu tool.

```
lookup_customer_activity          → wraps identify_customer
search_product_activity           → wraps search_product
get_product_activity              → wraps get_product
get_price_activity                → wraps get_price
check_stock_activity              → wraps check_stock
deduct_stock_activity             → wraps deduct_stock (Class D)
check_payment_activity            → wraps check_payment
execute_payment_activity          → wraps execute_payment (Class D)
get_payment_status_activity       → wraps get_payment_status
create_draft_order_activity       → wraps create_draft_order
get_order_draft_activity          → wraps get_order_draft
update_order_draft_activity       → wraps update_order_draft
create_transaction_activity       → wraps create_transaction (Class D)
write_audit_event_activity        → audit trail
send_telegram_message_activity    → notification
```

Tools `get_customer`, `get_plafon`, `get_order`, `get_order_history`, `get_order_status`, `add_order_item`, `remove_order_item` diakses langsung oleh ADK tanpa activity wrapper (read-only atau composite via `update_order_draft_activity`).

Workflow command tools (`start_order_workflow`, `confirm_order`, `cancel_order`, `request_human_handover`) tidak menjadi activity — mereka adalah Signal/Update ke workflow.

## 8. Idempotency Key Format (SoT)

```
telegram_update_id      : <raw update_id dari Telegram>
order                   : <order_id>
transaction             : GOODANG:{order_id}
stock                   : GOODANG-STOCK:{transaction_id}
payment                 : GOODANG-PAY:{transaction_id}        ← BARU (was TBD)
handover                : GOODANG-HANDOVER:{order_id}           ← BARU
```

Retry tidak boleh membuat side effect kedua. Semua operasi dengan side effect wajib idempotent.

## 9. Confirmation Keyword Mapping (SoT)

### 9.1 Aturan

- Case-insensitive — normalisasi ke uppercase sebelum match.
- Hanya valid jika `current_state == WAITING_CONFIRMATION`.
- Di luar state itu, kata apa pun TIDAK boleh dianggap konfirmasi transaksi.

### 9.2 Keyword map

```
CONFIRM → YA, IYA, OKE, OK, SETUJU, JADI, LANJUT, PESAN, YES, YAP, BETUL
MODIFY  → UBAH, GANTI, RUBAH, EDIT, REVISI, UBAH PESANAN
CANCEL  → BATAL, CANCEL, GAK JADI, BATALKAN, TIDAK JADI
```

### 9.3 Invariant

```
IF state != WAITING_CONFIRMATION:
    "YA" tidak boleh finalize transaction

IF customer_confirmed != true:
    create_transaction forbidden

Transition WAITING_CONFIRMATION → CONFIRMED hanya boleh via event CUSTOMER_CONFIRM
Transition ke CONFIRMED dari state lain DILARANG
```

### 10.2 Formula

```

cooked_qty  = 0 jika tidak applicable (default), formula TBD per SKU category

```

```

```

```

## 11. Timeout & Retry Policy (SoT)

### 11.1 Temporal retry policy

```
initial_interval     = 2 seconds
backoff_coefficient  = 2
maximum_interval     = 30 seconds
maximum_attempts     = 5
```

### 11.2 Activity timeout

```
read activity          : 5–10 seconds
draft write activity   : 10–30 seconds
workflow command       : 10–30 seconds
transaction activity   : up to 30 seconds
stock mutation activity: up to 30 seconds
telegram send activity : 10–15 seconds
```

### 11.3 Business timeout

```
WAITING_CONFIRMATION → EXPIRED : 30 minutes
```

Draft expired tidak boleh otomatis menjadi transaction.

### 11.4 Retryable vs Non-Retryable

Retryable (Temporal auto-retry):

```
TIMEOUT
SERVICE_UNAVAILABLE
NETWORK_FAILURE
TEMPORARY_5XX
```

Non-retryable business errors (return sebagai kondisi bisnis, jangan retry tanpa batas):

```
CUSTOMER_NOT_FOUND
PRODUCT_NOT_FOUND
PRODUCT_AMBIGUOUS
INVALID_QUANTITY
INSUFFICIENT_STOCK
PRICE_MISMATCH
INSUFFICIENT_PAYMENT_LIMIT
ORDER_INVALID_STATE
CONFIRMATION_REQUIRED
```

## 13. Change Management

Perubahan pada salah satu item di §2–§11 wajib:

1. Update `docs/0. GOODANG_CONTRACT.md` terlebih dahulu.
2. Jalankan `scripts/check-contract-drift.sh` (lihat §14).
3. Update dokumen lain yang referensi.
4. Version bump di header dokumen ini.

## 14. Anti-Drift CI Check

Script `scripts/check-contract-drift.sh` wajib dijalankan pada setiap PR yang menyentuh file `docs/` atau `app/**/*.md`. CI workflow ada di `.github/workflows/contract.yml`.

Script tambahan:
- `scripts/check-tool-registry-sync.py` — verifikasi sync `app/tools/registry.yaml` dengan `docs/0` §3 (canonical tool names). Pastikan Class D tools tidak ada di ADK registry.

Check yang dijalankan:

1. Verifikasi 14 duplikat file antara `docs/` dan `app/*`/`knowledge/`/`evaluation/` tetap byte-identical.
2. Deteksi ghost state (`WAITING_CUSTOMER`, `CUSTOMER_CONFIRMATION`, `VALIDATION` sebagai state).
3. Deteksi nama tool kontradiktif (`lookup_customer` tanpa suffix `_activity`, `add_item`, `cancel_draft`, dll).
4. Deteksi error code kontradiktif (`RESOLVED`, `VALID` tanpa prefix, `UNAVAILABLE` tanpa prefix, `HANDOVER` tanpa suffix).
5. Verifikasi tool registry sync (Class A/B/C/D, forbidden names).

Jika salah satu check gagal, PR tidak boleh di-merge.
