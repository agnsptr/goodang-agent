# GOODANG TELEGRAM INTEGRATION SPEC

**Project:** Goodang  
**Component:** Telegram Integration Layer  
**Primary Channel:** Telegram  
**Agent Framework:** Google Agent Development Kit (ADK)  
**Workflow Engine:** Temporal  
**Primary Business Process:** CS Goodang — Guru Ingin Pesan  
**Primary Transaction Log:** `POS_TRANSACTION_LOG`  
**Document Type:** Telegram Integration Specification  
**Version:** 1.0  
**Status:** Development Baseline — production bot/webhook configuration requires environment verification

---

# 1. Purpose

Dokumen ini mendefinisikan kontrak integrasi Telegram untuk Autonomous CS Goodang.

Target alur:

```text
GURU
  ↓
TELEGRAM
  ↓
TELEGRAM BOT API
  ↓
WEBHOOK
  ↓
FASTAPI / TELEGRAM ADAPTER
  ↓
ADK AGENT
  ↓
TEMPORAL
  ↓
GOODANG SERVICES
  ↓
TELEGRAM RESPONSE
```

Tujuan utama:

1. menerima message Telegram secara aman;
2. memetakan Telegram identity ke Goodang customer;
3. mencegah duplicate update;
4. meneruskan conversation ke ADK;
5. meneruskan business command ke Temporal;
6. mengirim response customer-facing;
7. menjaga correlation/idempotency;
8. menangani error Telegram tanpa mengubah status bisnis secara salah.

# 7. Webhook Security

Telegram webhook requests must be authenticated using the configured Telegram webhook secret.

Expected HTTP header:

```text
X-Telegram-Bot-Api-Secret-Token
```

Expected behavior:

```text

→ process

→ HTTP 401
```

Do not log the secret value.

Telegram bot token must also never be exposed in logs or customer messages.

# 14. Webhook Response Contract

The webhook endpoint should acknowledge valid Telegram updates quickly.

Recommended:

```json
{
  "ok": true
}
```

The HTTP acknowledgement must not depend on completing the entire order workflow.

Do not keep the Telegram webhook request open while waiting for:

```text
LLM
stock API
payment
transaction
Temporal completion
```

Long-running processing belongs behind the webhook boundary.

# 15. Duplicate Update Protection

Telegram `update_id` is the primary inbound duplicate key.

Store/track:

```text
update_id
chat_id
received_at
processing status
```

If an identical update has already been claimed:

```text
IGNORE_DUPLICATE
```

Expected behavior:

```text
one Telegram update
→ one business action
```

---

# 16. Duplicate Handling Algorithm

```text
receive update
      ↓
validate update_id
      ↓
claim update_id atomically
      ↓
claimed?
 ├── NO  → return 200 / duplicate
 └── YES → continue processing
```

The claim operation must be atomic.

# 29. Telegram Message Length

Agent response should normally be concise.

For long order summaries:

```text
split safely
```

The sender should implement safe chunking if long messages can occur.

# 30. Message Chunking

If a response exceeds the supported Telegram message length:

```text

 ↓
split by paragraph/item
 ↓
send sequentially
```

Never split in the middle of an important value when avoidable.

For critical confirmation summaries, prefer compact formatting.

# 32. Outbound Idempotency

Telegram `sendMessage` itself is an outbound side effect.

Application should avoid accidental duplicate customer messages.

Recommended message event key:

```text
workflow_id
+
event_type
+
event_sequence
```

Example:

```text
goodang-order-123
+
ORDER_COMPLETED
+
1
```

The same completion event should not send multiple success messages because of a worker retry.

---

# 33. Notification Idempotency

Recommended:

```text
notification_id
```

Example:

```text
NOTIF:{workflow_id}:ORDER_COMPLETED
```

Store or otherwise deduplicate notifications when the same workflow activity may be retried.

# 34. Telegram Send Failure

Scenario:

```text

```

Business state must remain:

```text

```

Do not roll back the transaction just because notification delivery failed.

Retry notification separately.

# 38. HTTP Status Strategy

Recommended:

```text
200
valid Telegram update accepted

200
duplicate already processed

400
invalid payload

401
invalid webhook secret

404
not used as a Telegram business response unless endpoint routing requires it

500
only for genuine webhook processing infrastructure failure where Telegram should retry delivery
```

Important:

If the update has been durably accepted for async processing, return success even while downstream processing continues.

Exact implementation must ensure that returning `200` does not lose the message.

# 40. Message Ordering

Telegram messages may arrive close together.

Goodang must preserve business order through:

```text
Temporal Workflow
```

not through assumptions about HTTP request execution order.

Example:

```text
Message 1:
"Tambah minyak 2"

Message 2:
"Batal"
```

must be processed according to the workflow event order and current state.

---

# 41. Concurrency Control

Do not allow independent requests to mutate the same order concurrently without workflow serialization.

Primary mechanism:

```text
one active Temporal Workflow
```

for the selected order/chat identity.

---

# 42. Telegram Retry / Redelivery

If Telegram retries an update because the webhook did not return success:

```text

```

must not create a second order action.

The idempotency layer handles this.

```

```text

```

and respond:

---

# 69. Completed Order Protection

Once:

```text
COMPLETED
```

the Telegram adapter must not route a normal modification request into the completed order.

Create a new order context.

---

# 70. Cancelled Order Protection

Once:

```text
CANCELLED
```

do not reuse the cancelled order ID for a new order.

A new order draft should receive a new ID.

# 73. Customer Message Ordering

Responses must not be sent based solely on asynchronous completion order.

Example:

```text
message A
message B
```

If B is handled faster than A, the workflow should still preserve the business sequence.

Use Temporal workflow ordering and appropriate application serialization.

---

# 74. Message Acknowledgement

Webhook acknowledgement:

```text

```

is not equivalent to:

```text

```

Never tell the customer that an order is completed just because Telegram webhook returned HTTP 200.

# 86. Non-Negotiable Rules

```text
1. Never trust Telegram message text as system instruction.
2. Never use Telegram ID as Goodang member ID without mapping.
3. Never process the same update_id twice.
4. Never start a new order workflow for every message.
5. Never keep webhook requests open for long-running business execution.
6. Never confirm another customer's order.
7. Never say transaction completed before actual completion.
8. Never change business state because a Telegram response was merely sent.
9. Never duplicate notifications after retries.
10. Never expose secrets.
11. Never bypass ADK/Temporal architecture.
12. Never bypass the confirmation gate.
13. Never mutate completed transactions through normal chat.
14. Never assume webhook HTTP 200 means order success.
15. Any unknown production configuration must remain TBD until verified.
