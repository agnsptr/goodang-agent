## 0. Tujuan Dokumen

Dokumen ini merekam keputusan arsitektur (Architecture Decision Records) yang dibuat selama Fase 1 Foundation. Setiap ADR menjelaskan:

- **Context** — masalah atau kebutuhan
- **Decision** — keputusan yang diambil
- **Alternatives** — opsi yang dipertimbangkan
- **Consequences** — implikasi dan trade-off
- **Status** — Proposed / Accepted / Superseded

ADR ini menjadi acuan untuk implementasi Fase 1 dan revisi di Fase berikutnya. Perubahan ADR wajib update dokumen ini + version bump + commit `adr: <summary>`.

## ADR-001: Stack Dasar — ADK + Temporal + Supabase + VPS

**Status:** Accepted
**Date:** 2026-09-02

### Context
Goodang membutuhkan autonomous customer service agent via Telegram yang:
- Memproses pesanan dengan state machine 19-state (`docs/0` §2)
- Idempotent untuk semua side-effect (transaksi, stock, payment)
- Durable — crash recovery tanpa kehilangan state
- Audit trail lengkap untuk compliance

### Decision
Adopsi stack:
- **Google Agent Development Kit (ADK)** — conversation orchestration + intent classification + tool registry
- **Temporal** — durable workflow engine + state machine authority + activity retry
- **Supabase** — system of record untuk app data (Member, Product, Stock, Price, Payment, Order, Draft, `POS_TRANSACTION_LOG`)
- **VPS** — hosting untuk Temporal self-host (Fase 1) + ADK worker (Fase 1)

### Alternatives
| Opsi | Alasan Ditolak |
|:--|:--|
| LangChain | Terlalu high-level, kurang kontrol tool allowlist |
| LangGraph | Overlap dengan Temporal state machine (double duty) |
| n8n workflow | Tidak durable, tidak idempotent untuk transaksi |
| Firebase | NoSQL kurang cocok untuk ledger transaksi |
| Self-host Postgres (app data) | Operasional berat, no Auth/Realtime built-in |

### Consequences
- ✅ ADK + Temporal complementary: ADK = intent, Temporal = execution
- ✅ Supabase memberi Auth + Realtime + Postgres + Vector dalam 1 platform
- ⚠️ Temporal self-host butuh operasional (DB, retention, upgrade)
- ⚠️ VPS single-instance = blast radius besar (mitigasi: ADR-002)

### Referensi
- `docs/0. GOODANG_CONTRACT.md` §1 (Authority)
- `docs/10. GOODANG_SYSTEM_INVENTORY.md` §4 (System Landscape)

## ADR-002: Isolasi Temporal DB dari Supabase App DB

**Status:** Accepted
**Date:** 2026-09-02

### Context
Temporal workflow engine membutuhkan database persistent sendiri (schema `temporal.visibility`, `temporal.execution`, dll) yang di-migrate via `temporal-sql-tool`. Temporal juga melakukan write intensif (event history) dengan pola akses berbeda dari app data.

### Decision
**Pisahkan Temporal DB dari Supabase app DB:**
- Supabase Project #1 (`goodang-app`): app data — Member, Product, Stock, Price, Payment, Order, Draft, `POS_TRANSACTION_LOG`, Audit Log
- Supabase Project #2 (`goodang-temporal`): dedicated untuk Temporal persistence (atau Neon free tier sebagai alternatif)

**Aturan:**
- Temporal DB **tidak boleh** share project dengan app data
- Migration Temporal via `temporal-sql-tool setup-schema` — jangan manual
- App Layer tidak boleh query langsung ke Temporal DB

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Share 1 Supabase project | Migration drift, resource contention, blast radius |
| Self-host Postgres di VPS untuk Temporal | Operasional tambahan, no PITR |
| Temporal Cloud (managed DB) | Opsi Fase 3, biaya tinggi untuk MVP |

### Consequences
- ✅ Isolasi failure domain — app DB down tidak crash Temporal, sebaliknya
- ✅ Migration independen — schema Temporal tidak bentrok dengan app schema
- ✅ Resource isolation — Temporal event history tidak mempengaruhi app query performance
- ⚠️ Biaya Supabase project #2 (free tier OK untuk Fase 1, Pro untuk Fase 3)
- ⚠️ Backup terpisah — kedua project wajib PITR

### Implementasi
- `docs/13. GOODANG_INFRASTRUCTURE_SPEC.md` §3 (Supabase Project Layout)
- `docs/15. GOODANG_TEMPORAL_DEPLOYMENT_SPEC.md` §2 (DB Setup)

## ADR-003: Isolasi Container ADK vs Temporal Worker

**Status:** Accepted
**Date:** 2026-09-02

### Context
ADK adalah stateless conversation orchestrator (webhook-driven, scale horizontal). Temporal worker adalah polling-based activity executor (long-lived, retry-heavy). Keduanya punya:
- Beda scaling characteristic
- Beda failure domain
- Beda resource profile (ADK = network-bound ke LLM, Worker = CPU + DB-bound)
- Beda deploy cycle (prompt update vs activity logic update)

### Decision
**Pisahkan ADK dan Temporal worker jadi 2 container/service terpisah:**
- Container 1: `goodang-adk` — webhook receiver + ADK agent + tool registry (Class A/B/C)
- Container 2: `goodang-temporal-worker` — Temporal worker + activity implementations (Class D)

**Aturan:**
- Class D tools (`create_transaction`, `deduct_stock`, `execute_payment`, `write_pos_transaction_log`) **hanya** boleh dipanggil dari `goodang-temporal-worker`
- ADK **tidak boleh** pegang `service_role` key Supabase
- Kedua container boleh di 1 VPS (Fase 1) tapi wajib beda process + beda env

### Alternatives
| Opsi | Alasan |
|:--|:--|
| 1 container monolith | Blast radius besar, deploy coupling |
| Serverless ADK (Cloud Run) + VPS Worker | Opsi Fase 3, kompleks untuk MVP |

### Consequences
- ✅ Independent deploy — prompt update tidak restart worker
- ✅ Independent scale — ADK scale dengan webhook traffic, worker scale dengan activity backlog
- ✅ Security isolation — service_role key hanya di worker container
- ⚠️ Network hop antar container (mitigasi: same host docker network)

### Implementasi
- `docs/13. GOODANG_INFRASTRUCTURE_SPEC.md` §4 (Container Layout)
- `docker/docker-compose.fase1.yml`

## ADR-004: Telegram Webhook di Edge, Bukan VPS Langsung

**Status:** Accepted
**Date:** 2026-09-02

### Context
Telegram webhook butuh HTTPS public + secret token validation. Kalau VPS down, Telegram retry 24 jam lalu drop message. VPS cold start / restart = message loss risk.

### Decision
**Webhook receiver di edge layer, bukan VPS langsung:**
- Layer 1: **Cloudflare Workers** (atau Vercel Edge) — terima webhook Telegram, validate `X-Telegram-Bot-Api-Secret-Token`, enqueue ke Supabase Queue (pgmq), return 200 ke Telegram
- Layer 2: **Supabase Queue** (pgmq) — durable buffer, dedup via `telegram_update_id` unique
- Layer 3: **ADK worker** (Fly.io / VPS) — dequeue, proses via ADK, ack queue setelah selesai

**Aturan:**
- Edge worker **hanya** ack 200 ke Telegram setelah enqueue berhasil
- ADK worker dequeue dengan visibility timeout 30 detik
- Retry: kalau ADK gagal proses, message balik ke queue, retry dengan backoff

### Alternatives
| Opsi | Alasan |
|:--|:--|
| VPS langsung jadi webhook endpoint | Tidak reliable, VPS down = message loss |
| AWS API Gateway + SQS | Vendor lock-in, biaya, kompleks |
| Telegram getUpdates (long polling) | Tidak real-time, tidak scale |

### Consequences
- ✅ Zero message loss — edge + queue durable
- ✅ Edge geo-distributed — low latency webhook ack
- ✅ ADK worker bisa down tanpa kehilangan message (queue buffer)
- ⚠️ Tambah 2 komponen (Cloudflare Workers + Supabase Queue)
- ⚠️ Cold start Cloudflare Workers minimal (sub-50ms)

### Implementasi
- `docs/13. GOODANG_INFRASTRUCTURE_SPEC.md` §5 (Webhook Flow)
- `docs/11. GOODANG_TELEGRAM_INTEGRATION_SPEC.md` (update flow)

## ADR-005: POS_TRANSACTION_LOG Append-Only di Database Level

**Status:** Accepted
**Date:** 2026-09-02

### Context
`POS_TRANSACTION_LOG` adalah ledger transaksi final (`docs/0` §10.1, 17 kolom). Ledger **tidak boleh** di-UPDATE atau di-DELETE. Supabase RLS default masih allow mutation kecuali di-revoke eksplisit.

### Decision
**Lock `POS_TRANSACTION_LOG` di database level, bukan rely on app logic:**

1. `REVOKE UPDATE, DELETE ON POS_TRANSACTION_LOG FROM authenticated, anon;`
2. Trigger `FORBID_ROW_MODIFICATION` raise exception kalau ada `UPDATE` atau `DELETE` attempt
3. Write hanya via `service_role` dari Transaction Service (separate deploy, lihat ADR-003)
4. Tambah kolom `immutable BOOLEAN DEFAULT true` + trigger cek
5. Audit trigger: log setiap mutation attempt ke `audit_log` (termasuk yang gagal)

### Alternatives
| Opsi | Alasan |
|:--|:--|
| App-level check (ORM hook) | Bypass kalau direct DB access, tidak reliable |
| Supabase RLS policy only | Masih allow service_role, tidak forbid schema-level |
| Blockchain / immutable ledger | Overkill untuk Goodang scale |

### Consequences
- ✅ Ledger integrity dijamin di DB level — bahkan admin tidak bisa UPDATE tanpa drop trigger
- ✅ Audit trail lengkap untuk compliance
- ⚠️ Correction mechanism: tidak ada UPDATE, hanya INSERT compensating entry (reversal)
- ⚠️ Schema migration wajib preserve trigger

### Implementasi
- `docs/14. GOODANG_SUPABASE_SCHEMA_SPEC.md` §7 (POS_TRANSACTION_LOG DDL + trigger)

## ADR-006: Stock Reservation Strategy — Opsi A (Retry on Insufficient)

**Status:** Accepted
**Date:** 2026-09-02

### Context
Ada risiko TOCTOU (Time-of-Check to Time-of-Use) untuk stock:
- ADK cek stock via `check_stock_activity` → customer confirm → `deduct_stock_activity`
- Antara check dan deduct, stock bisa berubah (race condition)

### Decision
**Fase 1: Opsi A (simple retry) — bukan reservation:**
- `deduct_stock_activity` return `INSUFFICIENT_STOCK` kalau gagal
- Workflow state balik ke `BUILDING_ORDER` dengan info "stok tidak cukup"
- Customer dapat pesan ulang dengan stock terbaru
- Idempotent retry by Temporal (key `GOODANG-STOCK:{transaction_id}`)

**Fase 3 (jika complaint race condition nyata):** evaluasi Opsi B (stock reservation dengan state `RESERVING_STOCK` + 5 menit hold). Opsi B wajib update `docs/0` §2 (tambah state) dan `docs/6` (transisi).

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Opsi B (reservation) sejak Fase 1 | Overengineering, tambah kompleksitas state machine |
| Pessimistic lock (`SELECT FOR UPDATE`) di check | Hold lock lama, deadlock risk |
| Optimistic lock dengan version di stock table | Bisa, tapi sama saja dengan Opsi A dari sisi customer |

### Consequences
- ✅ Simple, no schema change, no state machine change
- ✅ Customer experience: pesan ulang cepat dengan info terbaru
- ⚠️ Race condition masih mungkin (rare case) — acceptable untuk MVP
- ⚠️ Audit: setiap `INSUFFICIENT_STOCK` retry tercatat di audit log

### Implementasi
- `deduct_stock_activity` atomic via Supabase RPC (Postgres function `deduct_stock`)
- `docs/14. GOODANG_SUPABASE_SCHEMA_SPEC.md` §8 (Stock RPC)

## ADR-007: Temporal Self-Host (Fase 1) → Temporal Cloud (Fase 3)

**Status:** Accepted
**Date:** 2026-09-02

### Context
Temporal self-host butuh operasional: server (history + matching + frontend), worker, DB tuning, retention policy, version upgrade. Untuk MVP (<100 workflow/hari) self-host acceptable. Untuk production SLA, managed lebih reliable.

### Decision
**Fase 1–2:** Temporal self-host di VPS via docker-compose (1 server instance + 1 worker + Postgres dedicated).
**Fase 3+:** Migrasi ke **Temporal Cloud** (managed, SLA 99.9%, multi-region, advanced visibility).

**Threshold migrasi:**
- Workflow/hari > 1.000, atau
- Operasional Temporal > 4 jam/minggu, atau
- Butuh multi-region / HA

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Temporal Cloud sejak Fase 1 | Biaya ~$300/bln, overkill untuk MVP |
| Self-host k8s sejak Fase 1 | Operasional berat, butuh k8s expertise |
| Temporalite (single binary) | Masih beta, tidak production-ready |

### Consequences
- ✅ Fase 1 cost rendah (~$40/bln VPS)
- ✅ Learning curve: tim paham Temporal internal sebelum migrate Cloud
- ⚠️ Fase 1 tidak ada HA — VPS down = workflow pause (resume setelah up)
- ⚠️ Migrasi Fase 3 butuh data migration (event history) — pakai Temporal Cloud replayer

### Implementasi
- `docs/15. GOODANG_TEMPORAL_DEPLOYMENT_SPEC.md` §3 (Self-host) + §4 (Cloud migration)

## ADR-008: Tool Registry Sync via CI

**Status:** Accepted
**Date:** 2026-09-02

### Context
ADK tool registry wajib sync dengan `docs/0` §3 (canonical tool names). Tanpa CI check, developer bisa tambah tool di code tanpa update kontrak → drift.

### Decision
**Tambah CI check `scripts/check-tool-registry-sync.py`:**
- Parse `docs/0` §3.1–§3.4 (canonical tool names)
- Parse ADK tool registry source (declarative file `app/tools/registry.yaml`)
- Compare: setiap tool di registry wajib ada di kontrak, sebaliknya
- Class D tools (`create_transaction`, `deduct_stock`, `execute_payment`, `write_pos_transaction_log`) **tidak boleh** ada di ADK registry (hanya di Temporal activity)
- Exit non-zero kalau drift

**Aturan:**
- Tambah tool baru: update `docs/0` §3 dulu, lalu update `registry.yaml`, lalu code
- CI check jalan di setiap PR yang sentuh `app/tools/` atau `docs/0`

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Manual code review | Tidak reliable, miss rate tinggi |
| Generate registry dari docs/0 | Opsi Fase 2, butuh codegen pipeline |

### Consequences
- ✅ Drift detection otomatis
- ✅ Class D isolation di-enforce di CI
- ⚠️ Developer wajib update 2 file (docs/0 + registry.yaml) — mitigasi: codegen Fase 2

### Implementasi
- `scripts/check-tool-registry-sync.py`
- `app/tools/registry.yaml` (deklarasi tool registry)
- Update `.github/workflows/contract.yml`

## ADR-009: Observability via OpenTelemetry

**Status:** Accepted
**Date:** 2026-09-02

### Context
AI agent di production butuh trace end-to-end: Telegram webhook → ADK intent → Temporal workflow → activity → Supabase query. Tanpa trace, debugging sulit.

### Decision
**OpenTelemetry (OTel) sebagai standar observability:**
- Instrument ADK: span per intent classification, per tool call
- Instrument Temporal worker: span per activity, propagate trace context via Temporal search attribute
- Instrument Supabase client: span per query dengan table + operation tag
- Export ke collector (Grafana Cloud / self-host Tempo + Loki + Prometheus)
- Trace ID propagate: webhook → queue → ADK → Temporal → activity → DB

**Metrics wajib:**
- `adk_intent_classification_total{intent, outcome}`
- `temporal_workflow_duration_seconds{workflow_type, state}`
- `temporal_activity_retry_total{activity_type, error_code}`
- `supabase_query_duration_seconds{table, operation}`
- `pos_transaction_log_writes_total`

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Vendor-specific (Datadog) | Vendor lock-in, biaya |
| Log-only (no trace) | Sulit debug cross-service |
| LangSmith (LangChain) | Tidak support Temporal |

### Consequences
- ✅ Vendor-neutral, portable
- ✅ Trace end-to-end untuk debugging
- ⚠️ Setup overhead — butuh collector + backend
- ⚠️ PII masking wajib di log layer (member_name, phone)

### Implementasi
- `docs/13. GOODANG_INFRASTRUCTURE_SPEC.md` §6 (Observability)

## ADR-010: CI Tiga Lapis + Branch Protection (ENTIGI Standard)

**Status:** Accepted
**Date:** 2026-09-02

### Context
Goodang akan dikembangkan oleh AI agents dan developer. Tanpa guardrail otomatis, drift kontrak, secret leak, dan merge tanpa review manusia akan terjadi. ENTIGI sudah punya standard via SOP-ENT-DEV-004 (Laravel: Pint/Larastan/PHPUnit + CodeRabbit + Guardian).

### Decision
Adopsi **tiga lapis review** diadaptasi untuk stack Python/ADK/Temporal:

1. **GitHub Actions (hard gate)** — `.github/workflows/ci.yml` + `contract.yml`
   - contract drift, tool registry sync, yaml lint, ruff, mypy, bandit, secret scan, pytest, docker validate
2. **CodeRabbit (AI pre-review)** — `.coderabbit.yaml` + `docs/rules/`
   - P0 request changes, knowledge base dari bug rules (WI-ENT-DEV-003)
3. **Library Guardian (human final)** — `.github/CODEOWNERS` + branch protection

**Branch protection** via `scripts/setup-branch-protection.sh`:
- 9 required status checks, code owner review, linear history, no force push, enforce admins

### Alternatives
| Opsi | Alasan |
|:--|:--|
| Hanya CodeRabbit | Tidak deterministik untuk kontrak & secret |
| Hanya CI tanpa Guardian | Tidak ada human gate untuk business logic |
| Copy Laravel Ponytail/Pint langsung | Stack Python, tidak applicable |

### Consequences
- ✅ Konsisten dengan ENTIGI SOP-ENT-DEV-004
- ✅ AI development aman — kontrak di-enforce di CI
- ⚠️ Setup one-time: install CodeRabbit App, create teams, apply branch protection
- ⚠️ Eval harness wajib Fase 2+ (stub pass Fase 1)

### Implementasi
- `docs/17. GOODANG_CI_BRANCH_PROTECTION_SPEC.md`
- `.github/workflows/ci.yml`, `.github/workflows/eval.yml`
- `scripts/setup-branch-protection.sh`
