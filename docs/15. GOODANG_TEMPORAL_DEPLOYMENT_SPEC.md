## 2. DB Setup (Project #2: `goodang-temporal`)

### 2.1 Postgres requirement

- Version 15+ (sesuai Supabase default)
- Database: `temporal`
- User: `temporal` (hak akses penuh ke database `temporal`)
- Connection: direct (port 5432), **bukan** via pgBouncer (Temporal butuh session mode)

### 2.2 Schema migration via temporal-sql-tool

```bash
# Pull temporal-sql-tool image
docker pull temporalio/temporal-sql-tool:1.22

# Setup schema
docker run --rm --network=host temporalio/temporal-sql-tool:1.22 \
  --plugin postgres12 \
  --addr localhost:5432 \
  --db temporal \
  --user temporal \
  --password *** \
  setup-schema -v 1.0

# Setup visibility schema
docker run --rm --network=host temporalio/temporal-sql-tool:1.22 \
  --plugin postgres12 \
  --addr localhost:5432 \
  --db temporal \
  --user temporal \
  --password *** \
  setup-schema -v 1.0 --schema visibility
```

**Aturan:**
- Jangan manual CREATE TABLE — pakai `temporal-sql-tool`
- Version pin: `1.22` (sesuai Temporal server version)
- Upgrade Temporal server wajib jalankan `temporal-sql-tool update-schema` dulu

- Worker pegang `SUPABASE_SERVICE_ROLE_KEY` (bukan ADK)

## 4. Signal vs Update Policy

### 4.1 Update (sync, return value) — pilih untuk customer-facing command

| Tool | Type | Alasan |
|:--|:--|:--|
| `confirm_order` | **Update** | ADK butuh receipt konfirmasi sebelum reply ke customer |
| `cancel_order` | **Update** | ADK butuh receipt cancel sebelum reply |
| `request_human_handover` | **Update** | ADK butuh tahu handover created sebelum reply |

### 4.2 Signal (fire-and-forget) — pilih untuk system events

| Event | Type | Alasan |
|:--|:--|:--|
| `CUSTOMER_MESSAGE` | **Signal** | Tidak butuh receipt, workflow process async |
| `PRODUCT_SELECTED` | **Signal** | Trigger state transition, no reply needed |
| `CUSTOMER_PROVIDED_IDENTITY` | **Signal** | Input untuk `IDENTIFYING_CUSTOMER` state |

### 4.3 Update handler pattern

```python
@workflow.update_handler
async def confirm_order(self, confirmation_keyword: str) -> str:
    if self.state != "WAITING_CONFIRMATION":
        raise ApplicationError(
            "CONFIRMATION_REQUIRED",
            non_retryable=True,
        )
    if not self._is_valid_confirm_keyword(confirmation_keyword):
        raise ApplicationError(
            "CONFIRMATION_INVALID",
            non_retryable=True,
        )
    self.state = "CONFIRMED"
    workflow.upsert_search_attribute("goodang.state", "CONFIRMED")
    return "CONFIRMATION_ACCEPTED"
```

**Catatan:** `docs/0` §5 menyebut "Signal/Update" — dokumen ini disambiguasi: Class C workflow command tools = Update, customer input events = Signal. Update `docs/5` untuk refleksikan.

## 5. Timer untuk EXPIRED State

### 5.1 Implementation

```python
@workflow.workflow
class OrderWorkflow:
    @workflow.run
    async def run(self, order_id: str) -> str:
        # ... setup ...
        await workflow.wait_condition(lambda: self.state == "WAITING_CONFIRMATION")

        try:
            # Timer 30 menit (sesuai docs/0 §11.3)
            await workflow.execute_timer(
                timedelta(minutes=30)
            )
            # Timer fired → EXPIRED
            self.state = "EXPIRED"
            workflow.upsert_search_attribute("goodang.state", "EXPIRED")
            await workflow.execute_activity(
                "write_audit_event_activity",
                args={"event": "ORDER_EXPIRED", "order_id": order_id},
            )
            return "EXPIRED"
        except TemporalError:
            # Timer dibatalkan oleh Update (confirm/cancel)
            pass

        # ... continue happy path ...
```

### 5.2 Aturan

- **Jangan** pakai `time.sleep` atau `asyncio.sleep` — pakai `workflow.execute_timer`
- Timer dibatalkan otomatis kalau Update handler transition ke `CONFIRMED` atau `CANCELLED`
- 30 menit = business timeout (`docs/0` §11.3), **bukan** activity timeout
- Setelah EXPIRED: workflow terminal, customer harus mulai workflow baru

Default di self-host. Index by:

- `RunId`
- `StartTime`
- `ExecutionStatus`
- `CloseTime`

### 6.2 Advanced visibility (Fase 3)

Enable Elasticsearch backend atau Temporal Cloud. Index by custom search attributes:

```python
# temporal operator search-attribute create --name goodang.member_id --type Text
# temporal operator search-attribute create --name goodang.outlet_code --type Text

# Upsert di workflow
workflow.upsert_search_attribute({
    "goodang.state": "WAITING_CONFIRMATION",
    "goodang.chat_id": str(self.chat_id),
    "goodang.member_id": self.member_id,
    "goodang.outlet_code": self.outlet_code,

```

## 7. Retention Policy

### 7.1 Fase 1 (self-host)

```yaml
# dynamic_config.yaml
worker.RetryPolicyMaxAttempts: 10
frontend.historySizeLimit: 50000

# Retention via CLI (per namespace)
temporal operator namespace update --retention 30 goodang
```

- Workflow history retained 30 hari
- Setelah 30 hari, auto-delete (cleanup by Temporal server)
- Audit log di Supabase `audit_log` retained 7 tahun (compliance)

### 7.2 Fase 3 (Temporal Cloud)

- Retention 90 hari (default Cloud)
- Untuk compliance: export event history ke S3 sebelum delete (via Temporal replayer)

## 8. Migrasi ke Temporal Cloud (Fase 3)

### 8.1 Threshold migrasi (ADR-007)

- Workflow/hari > 1.000, atau
- Operasional Temporal > 4 jam/minggu, atau
- Butuh multi-region / HA

### 8.2 Migration steps

```text
1. Provisioning Temporal Cloud namespace: goodang.prod
2. Update worker config:
   - TEMPORAL_ADDRESS=goodang.prod.tmprl.cloud:7233
   - Add mTLS config (client cert + key + CA bundle)
3. Deploy worker baru (connect ke Cloud) — blue-green
4. Drain worker lama (self-host) — tunggu workflow in-flight selesai
5. Replayer: replay event history dari self-host ke Cloud (untuk workflow long-running)
6. Decommission self-host Temporal server + Postgres
```

### 8.3 mTLS config (worker)

```python
from temporalio.service import TLSConfig

client = await Client.connect(
    "goodang.prod.tmprl.cloud:7233",
    namespace="goodang.prod",
    tls=TLSConfig(
        client_cert=open("/etc/temporal/client.pem").read(),
        client_private_key=open("/etc/temporal/client.key").read(),
        server_root_ca_cert=open("/etc/temporal/ca.pem").read(),
    ),
)
```

## 9. Operasional Runbook

### 9.1 Backup

- **DB temporal:** PITR Supabase Project #2 (daily + 7-day retention)
- **Workflow history:** tidak perlu backup (redundant dengan DB) — retention 30 hari cukup
- **Audit log:** Supabase Project #1 `audit_log` (append-only, PITR)
- **Restore drill:** quarterly, dokumentasi di `docs/15` §9.4

### 9.2 Upgrade Temporal server

```bash
# 1. Cek compatibility matrix (Temporal version ↔ SQL schema version)
# 2. Backup DB (PITR snapshot)
# 3. Jalankan temporal-sql-tool update-schema
docker run --rm temporalio/temporal-sql-tool:1.23 \
  --plugin postgres12 --addr ... --db temporal --user temporal \
  update-schema -v 1.0

# 4. Pull image baru
docker pull temporalio/server:1.23

# 5. Rolling restart (Fase 1: stop → start, ada downtime singkat)
docker-compose up -d temporal-server

# 6. Smoke test: jalankan 1 workflow test
```

### 9.3 Recovery (VPS down)

```text
1. VPS-2 down → Telegram webhook tetap jalan (edge + queue buffer)
2. ADK (VPS-1) tetap jalan, tapi workflow stuck di waiting state
3. VPS-2 up → Temporal server resume, worker reconnect, workflow continue
4. Kalau DB corrupt → restore dari PITR, worker replay event history
5. Kalau DB irrecoverable → workflow in-flight fail, customer harus mulai ulang
   (acceptable untuk Fase 1, mitigasi Fase 3 dengan Cloud HA)
```

### 9.4 Monitoring

- Temporal UI: `http://vps-2:8233` (behind basic auth + IP allowlist)
- Metrics scrape: Prometheus scrape Temporal server `/metrics`
- Alert: `temporal_workflow_failed_total` > threshold, `temporal_activity_retry_total` p95 > 3

## 10. Security

- gRPC port 7233: internal-only (UFW deny from public)
- UI port 8233: behind basic auth + IP allowlist (CS lead office IP)
- DB Postgres: internal-only, tidak expose ke internet
- mTLS antar VPS: WireGuard tunnel
- Fase 3 (Cloud): mTLS ke Temporal Cloud (client cert dari Temporal Console)
